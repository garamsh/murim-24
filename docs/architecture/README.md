# Architecture

Current architecture of the system and the decisions behind it. This file is the index; workers read it before touching code, the PM keeps it honest.

## Structure

- **Responsibility documents** (one `.md` per domain or concern, e.g. `memory.md`, `gateway.md`) — the single source of truth for how the system is shaped *now*. To know the current state, read only these.
- **`adr/`** — the record of individual decisions: direction taken, context, rejected alternatives.
- **`structures/`** — one file per candidate architecture, read side by side at bootstrap to choose the shape the system takes. These are input to that decision and not a record of it: the choice is recorded as an ADR carrying the chosen file's §Signs the choice was wrong, that file's §Boundaries and dependency direction becomes `structure.md` (rules 6 and 7), and bootstrap deletes this folder once both have landed.

## Rules

1. **Responsibility document skeleton**: current decisions (consolidated) / rationale summary with links to the relevant ADRs / open questions. Do not copy ADR content — synthesize the present state.
2. **ADRs are append-only.** Once merged, the body is frozen. Exceptions: updating the status field (`accepted` → `superseded by ADR-XXXX`), fixing typos or broken links, and appending a dated entry under `## Errata` when the decision stands but a fact supporting it was wrong — the erratum names what falsified it, and the original text stays intact. A changed decision means a new ADR that supersedes the old one — never an edit.
3. **Decisions land in pairs.** A PR that adds or supersedes an ADR must update the affected responsibility documents in the same PR. A PR with only one of the two is rejected — the final state must always live in the responsibility documents.
4. Keep this index current: every responsibility document and every ADR is listed here. `structures/` is not — bootstrap deletes it, and an entry for a file that is about to go leaves the index wrong. An ADR covers a decision that changes a project rule — a settled choice that does not affect the rules does not earn one.
5. **Every domain or concern has a responsibility document.** The PR that introduces one adds its document; the PR that removes one deletes it. A system with no code yet has no more than `structure.md` (rule 6), and that is the correct state.
6. **Structural rules live in `structure.md`.** The shape chosen at bootstrap imposes rules — what the unit is, what may reference what, when a new one is earned — and they belong in the responsibility document for that concern, where a reviewer cites one by line and a correction is an ordinary edit. Not the ADR: rule 2 freezes that body, so superseding the choice of shape would be the price of fixing a rule's wording.
7. **A point the structural rules leave to the project is settled in an ADR** — the one recording the shape where the question is met at bootstrap, a later one where it is met later. Which side is taken decides what counts as a defect, so it is a decision under rule 4, and the ADR still holds the record after bootstrap. Nothing obliges a project to settle a question it has not met: until then the point waits under `structure.md`'s open questions, where it binds nothing, and moves into that document's current decisions when the project takes a side.
8. **Structural rules yield only to what a framework imposes.** Where `structure.md` and a convention file decide the same case differently, `structure.md` governs, unless the stack-specific file that applies decides it as its framework imposes it — the alternative fails to build or run, so the project cannot restate it. A stack file's spelling of a structural rule is not that: the rule it spells is `structure.md`'s. The shape chosen at bootstrap is this project's own refinement of what a stack-neutral file states for every project. A project with no `structure.md` meets no such conflict, and this rule asks nothing of it.

## Index

- `structure.md` — the shape the system is partitioned into and the rules it imposes
- `simulation.md` — the simulation core: what exists of it and the decisions it rests on
- `godot-adapter.md` — the GDExtension adapter through which Godot drives the core
- `world-generation.md` — how the core generates a region from a seed and data tables
- `adr/0001-partition-the-system-hexagonally.md` — the simulation is the application; every technology is an adapter
- `adr/0002-build-on-godot-with-a-cpp-simulation-core.md` — Godot as the presentation adapter, C++ as the core's language
- `adr/0003-build-the-core-with-cmake-googletest-and-llvm-tools.md` — CMake, C++17, GoogleTest and LLVM 22 tools for the core, installed from pinned PyPI wheels in CI
- `adr/0004-bind-the-core-to-godot-with-godot-cpp-through-cmake.md` — godot-cpp 10.0.0 pinned through CMake, the extension built beside the core, refusals returned to GDScript as null, GDScript tests through `run_tests.gd`, a pinned Godot 4.7.2 in CI
- `adr/0005-simulate-armies-at-three-levels-of-detail-in-fixed-point.md` — near, middle and far tiers that differ in data, armies that expand and collapse with exact totals, flow fields, a spatial hash, and fixed-point integers for determinism across builds; superseded by ADR 0017
- `adr/0006-resolve-every-skill-through-one-rule-scaled-by-count.md` — skills as data resolved by one rule for every body, scaled by the agents its user stands for, structures with durability and stages, and damage folded into count and strength; its scaling by count superseded by ADR 0017
- `adr/0007-move-each-army-at-its-own-phase-within-its-tier.md` — each army moves at a phase set by its index within its tier's interval, spreading a tier's movement over its ticks, while strikes stay on the tier's common tick; superseded by ADR 0017
- `adr/0008-present-the-world-top-down-in-real-time-as-pixel-art.md` — an orthogonal top-down view with one cell to one tile, real-time combat on the core's tick, and pixel art on a 16-pixel tile grid from Aseprite; superseded by ADR 0012
- `adr/0009-generate-a-region-from-data-tables-by-nearest-site-partitions.md` — terrain, faction and village data as tables, terrain and territory partitioned by nearest site, capitals spread by best candidate, villages owned in turn and placed among every corner that fits; its villages on free passable cells superseded by ADR 0024
- `adr/0010-keep-the-cores-inside-undivided.md` — the application's inside stays undivided, with no rings and no folder per subject area, its files flat in `core/`
- `adr/0011-steer-a-body-by-the-orders-every-army-follows.md` — every army follows an order of an objective and the skills it strikes with, given from data or through the `order` port alike; the player's body is a one-agent army born into a village, and its driver sets the focus on it before each tick; its focus rule superseded by ADR 0017
- `adr/0012-present-the-world-in-a-three-quarter-top-down-view.md` — a three-quarter top-down view on the 16-pixel grid with upright facades and bodies drawn by their footprint's bottom edge, structure footprints of several cells set by data, real-time combat, pixel art from Aseprite, and UI text in Korean first with English supported
- `adr/0013-give-structures-footprints-that-block-movement-in-every-stage.md` — structures cover footprints of cells, hit where a disc reaches them and blocking movement in every stage; objectives must be reachable; village templates laid out from the approved mockup, drawn among those with room, in a 128-cell region; its rule that every footprint blocks superseded by ADR 0022, and its rule that footprints block only from the world's creation by ADR 0023
- `adr/0015-run-the-village-life-cycle-from-structures-and-residents.md` — villages as structures and residents with a state derived on each read, repair as the strike rule with a negative structure effect, owners following residents, rebuilders from faction skills, and the destroyer recorded
- `adr/0016-lint-against-one-pinned-linux-sysroot-on-every-host.md` — `make lint` parses the core and the extension on every host against Ubuntu 24.04 headers pinned by SHA-256, so local and CI lint read the same standard library
- `adr/0017-make-every-npc-an-individual-and-every-army-a-roster.md` — every NPC a person with a stable identity, armies as rosters with conscription and disbanding, at most 500 living people, no levels of detail, a skill hitting each person once, and people a cell apart with standing crowds stepping aside for movers; supersedes ADRs 0005 and 0007 and parts of 0006 and 0011; its rule that people on the move give way to one another superseded by ADR 0020
- `adr/0018-change-a-factions-leader-by-duel-as-faction-data.md` — a faction's leader is a person, the Demonic Cult's succession is a duel given as faction data and fought by the one skill rule, a challenge rides the same order port for player and NPC, and allies of the old leader turn on a winner
- `adr/0019-draw-talent-and-lifespan-at-birth-and-bear-a-soul-again.md` — every birth, player or NPC, draws talent per discipline and a lifespan from `Life` data by one rule given the soul's history; people age out unless attainment extends them; a soul is born again into a family of a village in the same world with its draw widened by discipline, less with each life; the core keeps the calendar; its day fixed at 1,800 ticks in the core superseded by ADR 0021
- `adr/0020-let-a-person-on-the-move-ignore-people-behind-it.md` — a person on the move gives way to no one standing still and to no one behind it along its way, so a band queues through a one-cell gap into a walled village; supersedes ADR 0017's rule that people on the move give way to one another
- `adr/0021-let-people-marry-have-children-and-bear-family-names.md` — people marry and have children by data-defined kinship, one rule for everyone, children born through the one birth function while fewer than 500 live; family surnames and given names in Korean and romanised; founders born a founding age before the world; ticks per day as world data, superseding ADR 0019's fixed day
