# Dispatch a worker

## Start

1. Write the Task's text with `orca-ide orchestration task-create`, naming the role from `AGENTS.md` §Roles the worker holds, the issue it implements, the branch name per `git.md` §Branches, and the paths it may change. It needs a Run bound to the coordinator's terminal: where `orca-ide orchestration run-current --json` reads `.result.run` as `null`, bind one as §Host facts states before writing the Task. Where the change edits a convention file to meet an obligation another convention file states, the Task asks for the citation of that obligation in the pull request body and not in the convention file: `docs/convention/README.md` §Independence, "A convention file does not send the reader to another convention file", and §Stack-specific, "the files do not point at each other".
2. Start it: `orca-ide orchestration worker-start --task <task_id> --worktree new-child --agent claude --name <name> --base-branch main`. For a second round on the same worker, create a new Task with `orchestration task-create` and dispatch that into the worker's terminal. A reuse round does not take the first round's flags: read the set it takes from `orca-ide orchestration worker-start --help`, whose usage line and notes state which flags exclude `--terminal` and which are refused for an existing worktree.

## Confirm the three bindings

A start that exits 0 is the launcher's report, not an observation. Confirm each binding by asking the host:

1. **The worktree exists:** `orca-ide worktree list --json` lists it, and `git worktree list` shows it on the branch named.
2. **The role took:** `orca-ide orchestration worker-read --dispatch <dispatch_id> --source auto` shows the worker reading the issue and the files its role names, not acting as the role on its command line.
3. **It runs on its own:** a later `worker-read` shows new output, and none of it is a permission prompt waiting on input.

## Wait

1. Before the first wait, clear what is already queued: `orca-ide orchestration check --terminal <coordinator handle> --json`, without `--wait`. Where `.result.count` is above 0, read every message in `.result.messages[]` as one that may still be live — a `question` can have a worker blocked on it — then acknowledge the batch as step 3 does, and check again until `.result.count` reads 0. A wait over an unacknowledged batch returns that same batch at once, so it reads as nothing new while the messages behind it stay queued (§Host facts).
2. Wait on completion and its neighbours: `orca-ide orchestration check --terminal <coordinator handle> --wait --types "worker_done,escalation,question" --timeout-ms <n> --json`. Leaving `heartbeat` out of `--types` keeps the wait blocked across beats; with it in, every beat returns the wait.
3. On a nudge for a queued message, or a wait that returns well before its timeout, read the batch from `.result.messages[]`. Where it holds a `question`, take that message's `msg_` id from its entry before acknowledging: `orchestration reply --id <msg_id> --body <text>` answers by it, and once the batch is acknowledged, `orchestration worker-show --dispatch <dispatch_id> --json`, the coordinator-side view read for it, does not show it (§Host facts, which names the recovery from the worker's transcript). Then acknowledge the batch with `--ack <deliveryId>` taken from `.result.deliveryId`, and go back to step 2 where every message in it is a heartbeat. A heartbeat shows the worker is alive, not that it is done.
4. Judge whether a worker has settled by what it produced — commits on its branch (`git log origin/main..origin/<branch>`), a pull request (`gh pr list --head <branch> --json number,state`), a comment on its issue — rather than by its beats or its silence.

## Release

Releasing is three acts, each confirmed by asking the host afterwards rather than by the command's exit status.

1. **The terminal.** First confirm nothing the worker started still runs: `orca-ide terminal list --worktree <selector> --json`, and the processes whose working directory is in that worktree: `find /proc -maxdepth 2 -name cwd -lname '<worktree path>*'`. Then `orca-ide orchestration worker-release --dispatch <dispatch_id>`, or `orca-ide terminal close --worktree <selector> --all` for a terminal `worker-release` does not own. Confirm with `terminal list` again.
2. **The worktree.** `orca-ide worktree rm --worktree <selector>`; confirm with `git worktree list`.
3. **The branches.** Ask the host whether the work landed: `gh pr view <n> --json state,mergeCommit`, as its own command. On `MERGED`, delete the local branch where `worktree rm` retained it, with `git branch -D <branch>`. The repository's `delete_branch_on_merge` reads `true` (`gh api repos/garamsh/convention-driven-project --jq .delete_branch_on_merge`), so GitHub deletes the remote branch on merge. Confirm with `git branch --list <branch>` and `git ls-remote --heads origin <branch>`, both empty.
