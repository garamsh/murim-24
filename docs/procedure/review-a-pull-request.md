# Review a pull request

The order of the acts in a review of a pull request in this repository, the commands for each, and what the host does. What a review must carry is `docs/convention/review.md`; this file cites it and states none of it.

## Before the diff

1. List the changed paths without reading the diff: `gh pr diff <n> --name-only`.
2. Open `docs/convention/README.md` and, from its §Stack-neutral and §Stack-specific tables, pick every file whose Governs column covers a changed path. §Precedence there orders them where two apply.
3. Read those files, and `docs/convention/review.md` in full, from the files at the current `main` — `AGENTS.md` §Start here, every time gives the reason a remembered version is not read instead.
4. Where a changed path touches code or a decision, open `docs/architecture/README.md` too; its §Rules feed the Architecture row.
5. Read the task the pull request states — its issue and that issue's comments, or its Summary where it names no issue. `review.md` §What each check verifies, "Scope is measured against the task", names it as the measure.

## Reading the diff

1. Fetch first, so `main` is the one GitHub holds: `git fetch origin`.
2. Measure scope from the merge base: `git diff --stat origin/main...origin/<branch>`, three dots. In git 2.47.3, `git diff A...B` compares B against the merge base of A and B, while the two-dot `git diff A..B` compares the two tips, so every change merged to `main` after the branch was cut shows up as if the branch reverted it. `gh pr diff <n>` shows the same set the three-dot form does.
3. Check each changed line against the conventions read above. Each violation is cited as `review.md` §Citing violations states, and tagged as §Blockers and nits states.

## Confirming the run

The two checks this section serves are `review.md` §Submitting a review, "Confirm the checks belong to the head commit" and "A conclusion is not a verdict unless the run did the work".

1. Read the head: `gh pr view <n> --json headRefOid,headRefName`.
2. List the runs on the branch with the commit each ran on: `gh run list --branch <headRefName> --json databaseId,headSha,conclusion,event`. Take the run whose `headSha` equals `headRefOid`; a run on any other commit is not a run on the head.
3. Count the steps that ran: `gh run view <databaseId> --json jobs --jq '.jobs[] | {name, conclusion, steps: [.steps[] | {name, conclusion}]}'`.
4. Read what the steps selected: `gh run view <databaseId> --log`. In this repository the `make ci` step runs `make lint`, whose scripts each print a `checked <count> ... selected by: <command>` line; the counts are the work selected. An empty `gh run view --log` is not evidence that the run selected no work (§Host facts); where it prints nothing, read the job id with `gh api repos/garamsh/convention-driven-project/actions/runs/<databaseId>/jobs --jq '.jobs[].id'` and the log with `gh api repos/garamsh/convention-driven-project/actions/jobs/<job_id>/logs`.
5. In the log step 4 read, by whichever of its two commands printed it, read the runner image the job resolved to: in the `Set up job` step's `Runner Image` group, the `Image:` line, the `Version:` line under it, and the `Included Software:` link to that build; and read the log for any line announcing that the image is deprecated or will be retired. Where such a line appears, the PM opens an issue naming the image, the run and the line. This is the mover that `docs/convention/ci.md` §Verify a pinned dependency before adopting it, in the paragraph beginning "A reference no ecosystem can make immutable", owes the hosted runner label in `.github/workflows/ci.yml`'s `runs-on`, held for this repository's own pipeline. Basis that the log carries the image lines: run 38993653502, on head `5d465d0b4340cb1606500a981304de9b6a976b64`, printed `Image: ubuntu-24.04`, `Version: 20261012.334.1` and `Included Software: https://github.com/actions/runner-images/blob/ubuntu24/20261012.334/images/ubuntu/Ubuntu2404-Readme.md`, read with `gh run view 38993653502 --log` on 2026-10-17 UTC. That run carried no deprecation or retirement line, so it shows where such a line would be read and not that the log carries one.

## Posting the verdict

1. Write the body in a file, holding what `review.md` §Submitting a review names.
2. Where the reviewer opened the pull request from the same account, the state to submit is the one `review.md` §Single-account setups names. Where the reviewer also wrote the change, `review.md` §Reviewing your own change applies.
3. Submit it: `gh api --method POST repos/garamsh/convention-driven-project/pulls/<n>/reviews -f event=<APPROVE|REQUEST_CHANGES|COMMENT> -F body=@<file>`. `-F` reads a value starting with `@` from the named file; `-f` sends it as the literal string, per `gh api --help` in gh 2.46.0.
4. To merge, the method and the commit it leaves are `docs/convention/git.md` §PRs and §Commits, the second paragraph of §Commits, beginning "An author is a person", naming what the subject must carry: `gh pr merge <n> --squash --subject '<pr title> (#<n>)' --body-file <file>`, then read the commit on `main` against the squashed commits. The body is passed so that no line `git.md` §Commits keeps off the default branch reaches it: the bullet beginning "The commit that reaches the default branch contains only what the project put there", and that same second paragraph for an agent trailer. The subject passed to `--subject` is the subject that lands, so the number has to be in it. Take the `--subject` path shown above: a subject passed lands as passed, while the subject composed without one is measured only on pull requests of one commit whose subject was the title. Whichever path is taken, pass the body. §Host facts holds the readings each of these rests on, what a merge passing no body lands among them.
